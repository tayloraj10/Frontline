    - Raw bag/pound counts are **not lost** — every cleanup contribution traces back to a `cleanups` row with `metrics_small_bags`/`metrics_large_bags`/`metrics_pounds`, via `contributions.cleanup_id` (self-logs, organizer log-for-attendee) or `contributions.cleanup_event_id` (team-total split shares, joining to the event's own `cleanups` row). ## 13. Group event-as-route reverting to individual route

- [x] Root cause found and fixed: `list_campaign_cleanup_routes` (`backend/app/api/routes/cleanup_events.py`, the endpoint feeding the map's route polylines) had no time/status filter at all — it returned every route forever, unlike `list_campaign_cleanup_events` (point markers), which stops returning an event ~26h after it ends. The frontend (`CampaignMap.tsx`) derives a route's "is this a group event" styling (blue color, buffer corridor, past-greying, eventual disappearance) purely by checking whether the route's id is still present in the (already-filtered) events list — so once an event route aged out of that list, the route itself kept coming back from the routes endpoint and silently rendered as a permanent ad-hoc/individual route instead of disappearing. Fixed by applying the identical `status IN ('scheduled','in_progress')` + 26h-after-end expiry condition to group-event-linked routes in `list_campaign_cleanup_routes`; true ad-hoc (non-event) routes are untouched and still persist forever, as intended. No frontend change needed — once the backend stops returning the expired route, the existing `eventById.has(r.id)` logic naturally treats it as gone.
